# Plan — 모바일 DOM 런타임 최적화

## 목표

모바일 연타 중 DOM 전체 교체를 제거하고 초기 로드 및 프레임 지연을 측정 가능한 수준으로 개선한다

## 작업 범위

1. 모바일에서 네 탭의 변경 이벤트 비용·DOM 교체량·프레임 간격과 초기 번들/폰트 전송량을 계측한다.
2. 하단 패널의 연속 상태 변경을 짧은 렌더 예산 안에서 합치고 직접 조작은 즉시 반영한다.
3. HUD DOM 참조와 상태 문자열을 캐시해 값이 바뀐 노드만 갱신한다.
4. 폰트와 클라우드 시작 비용은 시각·데이터 회귀가 없는 항목만 최적화한다.
5. 단위·성능 E2E·기존 전체 E2E·실제 연타 플레이로 전후 수치와 기능을 검증한다.
6. Claude 독립 계획 리뷰와 구현 후 검증 리뷰의 지적을 로컬 근거로 재확인한다.

## 완료 결과

- 첫 반영 즉시 + 후속 최대 100ms 합류를 구현했다.
- 목표 탭은 ID 기반 부분 갱신으로 값 변경 시 전체 재생성을 제거했다.
- Firebase SDK는 첫 입력/5초 뒤로 지연하고 Analytics만 이벤트 시점까지 추가 지연했다.
- Firestore Lite는 저장 의미 변경 위험 때문에 교차리뷰 후 폐기하고 full SDK를 유지했다.
- 68 unit + build + 5 E2E + 상태 주입 없는 70초 플레이를 통과했다.

## 검증 계획

- `QA_BASE_URL=http://localhost:5178 node scripts/_mobileperformancetest.mjs` 전후 비교.
- `npm test`, `npm run build`, `git diff --check`.
- QA target guard와 preflight를 통과한 뒤 기존 Playwright 회귀 묶음 실행.
- 390×844 및 360×740에서 연타·탭 전환·스크롤 보존·오버플로·오류를 확인한다.

## 위험

- 렌더를 과도하게 늦추면 구매 가능 상태와 진행률이 뒤늦게 보일 수 있다.
- `innerHTML` 교체 빈도 변경이 직원/목표 탭 스크롤 보존과 직접 조작에 영향을 줄 수 있다.
- 클라우드 초기화를 늦추면 로컬 플레이 뒤 더 최신 원격 세이브가 도착하는 충돌 창이 늘 수 있다.
- 폰트 패밀리 축소는 작은 한글의 픽셀 선명도에 영향을 줄 수 있다.
- 성공선은 60회 연속 변경에서 패널 전체 교체 12회 이하, 전 탭 frame max 33ms 이하, emit p95 기준 대비 +0.5ms 이내다.
