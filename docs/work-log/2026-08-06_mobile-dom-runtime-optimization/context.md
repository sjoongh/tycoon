- 작업: 모바일 DOM 런타임 최적화

## 근거와 입력

- `GameState.processClick()`은 매 탭마다 `changed`를 발생시킨다.
- `DOMBottomPanel.refresh()`는 활성 탭을 매번 `innerHTML`로 전부 교체한다. 목표·감사 탭은 수십 개 노드를 포함한다.
- `DOMHud.refresh()`는 매 변경마다 같은 요소를 다시 검색하고 FAB 내부 HTML을 재생성한다.
- 감사 인장 선택 이중 렌더는 초기 탐색 출력의 잘림으로 생긴 가설이었고, 원본 재확인 결과 실제 코드는 한 번만 호출해 변경 대상에서 제외했다.
- 프로덕션 빌드 초기 앱 청크는 244.37kB(75.20kB gzip), Phaser 필수 청크는 1,208.06kB(330.08kB gzip)다.
- Firebase는 코드 분리돼 있지만 설정이 활성화되어 시작 직후 초기화된다. 세 Galmuri 폰트는 합계 약 1.46MB다.

## 제약

- Phaser는 게임 화면의 필수 런타임이므로 단순 지연 로딩 대상으로 보지 않는다.
- 보스·작전·피버·오프라인·감사 경제와 기존 시각 정체성은 바꾸지 않는다.
- UI 반응을 느리게 체감하지 않으면서 연타 중 DOM 전체 교체 빈도를 제한한다.
- 사용자 소유 `.omc/`, `.impeccable/` 변경은 범위에서 제외한다.

## 결정

- 변경 전·후를 같은 390×844 Playwright 계측으로 비교한다.
- 1차 목표는 선행 즉시·후행 합류 방식의 하단 패널 렌더 합치기와 HUD 노드·상태 마크업 캐시다.
- 초기 전송 최적화는 실제 네트워크 경쟁 항목인 폰트와 시작 직후 Firebase 초기화를 우선 검토한다.
