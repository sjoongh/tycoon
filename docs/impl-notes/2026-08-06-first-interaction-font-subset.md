# 2026-08-06 첫 조작·폰트 전송 최적화

## 목표 / 확정 사항

- 첫 조작 직후 Firebase 대형 청크가 핵심 게임 프레임과 경쟁하지 않도록 브라우저 idle에 예약한다.
- 기존 5초 절대 시작 상한과 랭킹 진입의 즉시 클라우드 연결은 유지한다.
- Galmuri9·14는 게임의 정적 글자만 담은 서브셋으로 교체하고, Galmuri11 full은 임의 한글 닉네임·입력을 위해 유지한다.
- 픽셀 크기별 폰트 역할, Firestore full SDK의 저장 의미, 게임 규칙은 바꾸지 않는다.

## Gate evidence

- 질문: `A` 첫 입력에서 Firebase를 idle 예약하되 5초 상한 유지 후 Galmuri9·14만 정적 글자 서브셋 / `B` Firebase만 / `C` 폰트만 중 선택을 요청했다.
- 사용자 답: `a로가자`
- 승인된 범위: A안의 클라우드 idle 예약, 5초 상한·랭킹 즉시 경로 유지, Galmuri9·14 정적 글자 서브셋, Galmuri11 full 보존, 관련 성능·시각·회귀 검증.
- 미승인 가정: Phaser 교체·지연, Firestore Lite 전환, Galmuri11 서브셋은 하지 않는다.

## 계획

1. 저사양 모바일 조건의 첫 조작 프레임과 폰트 요청·전송량을 기준 측정한다.
2. 첫 입력은 클라우드 idle 예약만 만들고, 랭킹은 즉시 시작하며, 5초 절대 타이머를 보존한다.
3. 소스의 정적 사용자 문구에서 코드포인트를 수집해 Galmuri9·14 서브셋을 재현 가능하게 생성한다.
4. 임의 한글 닉네임이 Galmuri11로 표시되는지, 기존 픽셀 크기별 렌더가 흐려지거나 잘리지 않는지 브라우저에서 비교한다.
5. 단위·빌드·성능·전체 E2E·직접 플레이로 검증한다.

## 판단 근거

- 현재 폰트 전송 1,506,654바이트 중 Galmuri9·11·14가 약 1.46MB다.
- Galmuri9·14는 정적 게임 UI와 Phaser 문구에 쓰이지만 Galmuri11은 사용자 닉네임·입력의 최종 한글 fallback 역할을 한다.
- Phaser는 게임 부팅의 동기 의존성이고 gzip 약 330KB이므로 이번 좁은 단계에서 분리하지 않는다.
- 클라우드 저장 의미를 지키기 위해 Firestore full SDK는 유지한다.

## 구현 결과

- 첫 pointer/keydown 이후 입력이 계속되면 750ms settle timer를 다시 시작한다. 입력이 잠잠해지면 `requestIdleCallback`에서 클라우드를 시작한다.
- 페이지 진입 5초 deadline은 별도 유지하며, 랭킹 이벤트는 예약을 취소하고 즉시 `startCloud()`를 호출한다.
- `subset-font@2.5.0` 개발 의존성과 `npm run fonts:subset`을 추가했다. `prebuild`가 이를 자동 실행하며, 원본 Galmuri9·14는 `tools/font-source/`에 보존하고 생산 빌드에는 정적 1,035 코드포인트 subset만 포함한다.
- Galmuri9·14 family 이름과 크기 매핑은 유지했다. DOM과 Phaser 모두 Galmuri11 full을 뒤 fallback으로 두어 새 문구·임의 한글의 누락을 막았다.
- 상태 주입 없는 직접 플레이도 외부 호스트를 차단해 실제 Firebase 데이터에 영향을 주지 않는다.

## 측정 결과

- 전체 폰트 실전송: 1,506,654 → 556,338바이트, 950,316바이트(-63.1%).
- Galmuri9: 429,336 → 20,112바이트(-95.3%), Galmuri14: 565,420 → 24,328바이트(-95.7%).
- 연속 pointer 입력 중 Firebase SDK 요청 0건, 마지막 입력 771.3ms 후 시작, 무입력 5초 deadline 4,932.6ms, 랭킹 즉시 경로 0.2ms.
- Chrome 실제 사용 폰트: 정적 작은 표본 `Galmuri9-Regular`, 굵은 표본·숫자 101 `Galmuri14-Regular`, 희귀 글자 `힣`만 `Galmuri11-Regular` fallback.
- 동일 입력으로 subset을 두 번 만들었을 때 SHA-256이 같았다.
- 4× CPU 기준 첫 조작의 기존 long task는 Firebase 요청보다 먼저 발생했다. Phaser 초기 부팅 비용으로 판단하며 이번 변경이 그 프레임을 줄였다고 주장하지 않는다.
