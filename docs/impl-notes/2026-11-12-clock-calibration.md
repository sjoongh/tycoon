# 서버 시계 보정 복구

## 문제
`calibrateClock()`은 `clock/{uid}`에 serverTimestamp를 쓰고 다시 읽어 오프셋을 잰다. 콘솔에서 관리하던 Firestore 규칙에 `clock` 경로가 없어 처음부터 항상 권한 오류로 조용히 실패했다. 모든 시각 판정이 기기 시계만 썼다.

## 변경
| 항목 | 내용 |
|---|---|
| 규칙 | `firestore.rules`를 리포로 옮겼다(기존 saves·scores 그대로). `clock/{uid}`는 본인만 읽기, 쓰기는 필드 `t` 하나 + `t == request.time`(서버 시각)일 때만 |
| 오프셋 저장 | 잰 값을 `gaepyo-clock-offset`에 저장하고 다음 실행 때 세이브 로드 전에 적용(`clock.restore()`). 오프라인 정산이 처음부터 보정된 시각을 쓴다 |
| 세션 중 보정 | 2초 이상 바뀌었을 때만 적용. 바뀐 만큼 `lastSeenAt`을 옮겨 다음 복귀 정산에서 부재 시간이 튀지 않게 한다. `lastSavedAt`은 되감김 판정 기준이라 두고 다음 저장 때 새 시각으로 찍힌다 |

## 검증
- 단위 테스트: 오프셋 저장·복원, 깨진 저장값, 보정 뒤 1분 부재가 정확히 1분으로 정산(285 통과).
- 규칙 테스트 API 10건(서버 시각 쓰기 허용, 과거 시각·추가 필드·남의 문서 거부, 기존 saves·scores 동작 유지) 통과 뒤 배포.
- 라이브: 새 익명 계정으로 서버 시각 쓰기·읽기 성공, 2020년 시각 쓰기 `PERMISSION_DENIED`, 남의 clock·saves 읽기 403. 테스트 계정·문서는 삭제했다.
- 브라우저(Date.now 3시간 늦춤): 오프셋 +3.000h 저장, `lastSeenAt` 보정, 새로고침 뒤 가짜 부재 시간 없음.

## 아직 확인할 것
- 규칙 배포 시점부터 구버전 클라이언트도 보정이 켜진다(오프셋 저장·`lastSeenAt` 보정 없음). 시계가 1시간 넘게 틀린 기기는 다음 저장 전까지 출석·주간 보상이 잠깐 보류될 수 있다. 영향 사용자 수는 미측정.
