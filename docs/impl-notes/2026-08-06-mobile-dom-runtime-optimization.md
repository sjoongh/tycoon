## 판단 근거
- 기준 60회 상태 변경에서 네 탭 모두 하단 패널을 60회 전부 교체했다. 목표 탭은 304개 DOM 노드를 포함했다.
- 기준 시설 탭 최악 프레임은 50.0ms였고 폰트 전송은 약 1.51MB, Firebase SDK 전송은 개발 서버 기준 약 1.46MB였다.
- 최종 패널 교체는 시설·직원·감사 60→11회, 목표 60→0회로 줄었다. 최종 frame max는 시설 24.7ms·직원 25.1ms·목표 18.4ms·감사 16.7ms, emit p95는 0.4~0.5ms였다.
- 첫 700ms Firebase SDK 요청은 0건이다. 첫 입력 뒤에는 저장 의미 보존을 위해 기존 Firestore full SDK를 사용하고, Analytics만 첫 분석 이벤트까지 지연한다.
- 폰트 단일화는 전용 픽셀 격자 선명도를 해칠 수 있어 구현하지 않았다.

## 구현 결과

- `DOMBottomPanel`의 첫 changed는 즉시 반영하고, 이어지는 changed만 100ms 예산으로 합친다.
- 직접 refresh·destroy에서는 timer/rAF를 취소하고, 숨김 중 만료된 trailing 갱신은 visibility 복귀 때 한 번 플러시한다.
- 목표 탭은 구조 서명에 출석·주간·일일 claim 상태·활성 목표 ID·완료/업적 상태를 포함한다. 구조가 같으면 `goal-id`로 진행률·수치·업적 퍼센트만 갱신한다.
- HUD는 세션 동안 한 번 생성되는 노드 참조를 캐시하고, 실제로 값이 달라진 text/style/HTML/ARIA만 쓴다.
- 클라우드 초기화는 첫 pointer/keydown 또는 5초 fallback에서 한 번만 실행한다. 랭킹 진입은 이를 즉시 강제하고 연결 중/실패 상태를 표시한다.
- Analytics는 실제 `logEvt`가 처음 호출될 때만 로드한다.
